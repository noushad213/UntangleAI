# UntangleAI implementation audit

Date: 2026-09-27

## Implementation update

The P0 and main P1 items identified below were addressed after the initial audit:

- Backend mutations now require administrator authorization, and reviewer identity comes from server configuration rather than request data.
- Public generation is rate-limited; cache bypass requires administrator authorization.
- CORS uses an explicit origin allowlist.
- Unmatched citizen tasks now call the live backend and generated workflows load in the visual roadmap UI.
- Generated roadmaps show review status, conflicts, missing details, and source evidence.
- Workflows expire after a configurable freshness window and lose reviewed status before regeneration.
- `/admin` provides a protected review queue; backend credentials remain server-side.
- Misleading document intake was removed from the landing search. Roadmap file copies are clearly described as unencrypted, device-local browser data.
- CI and an operations, backup, restore, and rollback runbook were added.

Remaining production work requires deployment configuration rather than more repository code: replace the internal HTTP Basic reviewer gate with the chosen identity provider, provide secrets through the hosting platform, run a live source-generation smoke test, and configure managed MongoDB snapshots.

## Executive result

The repository contains two strong but disconnected halves:

- The backend can discover official sources, reject unsafe URLs, extract HTML/PDF/OCR/Office content, chunk civic sections with provenance, ask Gemini or Groq for grounded workflow data, validate graph references and cycles, and cache results in MongoDB.
- The frontend provides a polished multilingual search experience, eight sample roadmaps, graph and list views, local progress tracking, document checklists, source links, contextual filters, and session resume.

The product described in the problem statement is not complete because the frontend does not call the live civic workflow backend. Citizens currently search a fixed in-memory catalog rather than generating a roadmap from official sites.

## Remaining findings

### P0 — Public callers can alter trusted civic data

- **Domains:** Security, authorization, data integrity
- **Evidence:** `POST /api/workflows/:id/verify`, `POST /api/municipalities`, and `POST /api/municipalities/:slug/issues` have no authentication or role check.
- **Impact:** Any caller who can reach the backend can mark generated guidance as verified or modify the municipality catalog. This breaks the central trust promise of the product.
- **Next action:** Add an established identity provider, require an administrator role on every mutation, record the authenticated reviewer ID, and add authorization tests before exposing the backend publicly.

### P1 — The live backend is not connected to the citizen flow

- **Domains:** Architecture, product, correctness
- **Evidence:** Frontend search, roadmap pages, and adaptation routes import `MOCK_ROADMAPS`. No frontend file calls `/api/query` or `/api/workflows/:id`.
- **Impact:** The main claim—generating a task-specific roadmap from fragmented government sites—is not available in the UI.
- **Next action:** Add a server-side frontend API client for `POST /api/query`, map backend graph JSON into `CivicProcess`, show generation/review status, and retain sample roadmaps only as an explicit demo or outage fallback.

### P1 — Unmatched tasks still become company registration

- **Domains:** Correctness, UX, trust
- **Evidence:** `HeroQueryInput.handleSubmit` routes every unmatched query to `/roadmap/pvt-ltd-delhi` with the original query in the URL.
- **Impact:** A citizen can ask for an unrelated service and receive confident but wrong instructions.
- **Next action:** Submit unmatched queries to the backend. If no reliable workflow can be generated, show a clear no-result state and links to official directories. Never substitute an unrelated process.

### P1 — Expensive public generation can be abused

- **Domains:** Security, reliability, cost
- **Evidence:** `/api/query` accepts unauthenticated requests and `forceRefresh`; no rate limiter or caller budget is applied at the HTTP boundary.
- **Impact:** A caller can trigger search, extraction, browser/OCR fallbacks, and model requests repeatedly, causing service exhaustion and API charges.
- **Next action:** Add per-IP and per-account limits, restrict `forceRefresh` to reviewers, cap concurrent jobs, and expose retry timing with HTTP 429 responses.

### P1 — Document handling is presented as processing but is local-only

- **Domains:** Product, privacy, UX
- **Evidence:** The landing upload passes only the file name as a `doc` query parameter. Roadmap attachments are stored as base64 in `localStorage` with status `verified_locally`.
- **Impact:** Uploaded documents do not influence roadmap generation. Sensitive identity documents may remain unencrypted in browser storage and can exceed browser quotas.
- **Next action:** Until secure processing exists, label attachments as a local checklist feature and remove the upload control from task generation. For real document intake, use explicit consent, file/type/size validation, encrypted private storage, malware scanning, retention limits, and deletion controls.

### P1 — Verification state and evidence do not reach citizens

- **Domains:** Trust, UX, data integrity
- **Evidence:** The backend returns `needs_review`, conflicts, missing information, sources, and evidence anchors; frontend `CivicProcess` sample data does not expose the backend review lifecycle.
- **Impact:** Users cannot distinguish reviewed facts from extracted suggestions or see unresolved conflicts.
- **Next action:** Show workflow status, last checked date, source per fact, evidence excerpts, conflicts, and missing information. Block “verified” presentation until an authorized review occurs.

### P2 — API hardening is incomplete

- **Domains:** Security, operations
- **Evidence:** Express uses `cors()` with default permissive origins. There is no explicit production origin list, request ID, or proxy trust policy.
- **Impact:** Browser origins are unrestricted, and production tracing/abuse investigation will be weak.
- **Next action:** Configure an environment-specific origin allowlist, reject unexpected origins, add request IDs, and document reverse-proxy settings.

### P2 — Frontend behavior has no automated regression tests

- **Domains:** Testing, reliability, accessibility
- **Evidence:** The frontend package has build and lint scripts only. There are no unit, component, or browser tests.
- **Impact:** Search routing, prerequisite locking, progress persistence, keyboard behavior, and the tracking workspace can regress without a failing gate.
- **Next action:** Add unit tests for roadmap mapping and progress rules, component tests for search and tracking, and one browser test covering query → roadmap → source → completion → resume.

### P2 — No CI, deployment, or recovery runbook

- **Domains:** CI/CD, availability, documentation, disaster recovery
- **Evidence:** No `.github/workflows` pipeline, deployment configuration, migration procedure, backup policy, or restore drill is checked in.
- **Impact:** Builds and tests depend on local discipline; MongoDB data recovery and rollback behavior are undefined.
- **Next action:** Add CI for backend tests, frontend lint/type/build, and secret scanning. Document environment variables, deployment, MongoDB backups, restore validation, and rollback.

### P2 — Cache freshness needs a policy

- **Domains:** Reliability, data integrity
- **Evidence:** Workflows and source checks store timestamps, but the citizen UI has no visible freshness threshold or stale-data behavior.
- **Impact:** Government fees, forms, and eligibility rules can change while old guidance continues to look current.
- **Next action:** Define freshness windows by service, schedule source rechecks, compare content hashes, mark changed workflows `outdated`, and prevent outdated workflows from appearing verified.

## Recommended delivery order

1. Secure all mutation and verification endpoints.
2. Connect one vertical slice: frontend query → backend `/api/query` → graph adapter → provenance/status UI.
3. Replace the unmatched-query fallback with no-result/error recovery.
4. Add query rate limits, concurrency limits, and reviewer-only refresh.
5. Build the authenticated review dashboard for sources, conflicts, missing facts, and verification history.
6. Decide whether citizen documents are local checklist artifacts or server-processed inputs, then implement the matching privacy model.
7. Add frontend tests and CI.
8. Add freshness jobs, monitoring, deployment, backup, and restore documentation.
